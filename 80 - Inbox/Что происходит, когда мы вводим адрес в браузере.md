> Мы отправляем запрос на **[google.com](https://google.com/)**

Полный сквозной путь: имя → IP → соединение → шифрование → HTTP → сервер → ответ → отрисовка. Плюс слои, которые обычно пропускают: NAT и маршрутизация.

---
## 0) Предварительно: что должно произойти

1. Узнать **IP** сервера (DNS).
2. Установить **соединение** (TCP).
3. **Зашифровать** канал (TLS).
4. Отправить **HTTP-запрос**.
5. Дождаться **ответа**.
6. **Отрисовать** страницу.

Но сначала пакет должен физически дойти до сервера — через домашнюю сеть, NAT и маршрутизаторы.

---

## 1) DNS Lookup

### 1.1) Проверка кэшей (от быстрого к медленному)

- кэш **браузера**
- кэш **ОС** (Windows: DNS Client, Linux: systemd-resolved/nscd)
- файл **/etc/hosts** (`C:\Windows\System32\drivers\etc\hosts`)
- кэш **роутера** (часто работает как DNS-прокси)

### 1.2) Запрос к DNS-резолверу

Идём на **рекурсивный резолвер**:
- DNS провайдера (из DHCP), либо
- публичный: `8.8.8.8` (Google), `1.1.1.1` (Cloudflare)

Резолвер сначала смотрит **свой кэш**. Если пусто — начинает **рекурсивный обход**.

### 1.3) Рекурсивный обход иерархии DNS

**Корневой сервер — что это?**  
Это 13 кластеров серверов по миру (`a.root-servers.net` … `m.root-servers.net`). Они знают **только одно**: где находятся серверы доменов верхнего уровня (TLD). IP `google.com` они не знают, но знают, кто отвечает за зону `.com`.

Цепочка:
1. **Корневой сервер** → «Не знаю `google.com`, но вот адрес серверов зоны `.com`».
2. **Сервер зоны `.com` (TLD)** → «Не знаю `google.com`, но вот авторитативные NS Google: `ns1.google.com` и т.д.».
3. **Авторитативный сервер `google.com`** → «Вот IP: `142.250.x.x`». Это конечный источник правды о домене.
### 1.4) Кэширование IP

Резолвер возвращает IP и кэширует его на время **TTL** (Time To Live) — сколько секунд запись считается актуальной. TTL задаёт авторитативный сервер.

Кэшируется:
- в **резолвере** (на TTL)
- в **ОС** (на TTL)
- в **браузере** (свой короткий кэш)
- иногда в **роутере**

## 1.5) NAT и маршрутизация

### Приватный vs публичный IP
- Компьютер в домашней сети: **приватный IP** (`192.168.1.5`) — в интернете не маршрутизируется.
- Роутер: **публичный IP**, выданный провайдером.

### Что делает NAT (Network Address Translation)

1. Пакет от `192.168.1.5:54321` уходит на роутер.
2. Роутер **подменяет** источник на свой публичный IP + **свой порт** (`203.0.113.7:1025`).
3. Запись `192.168.1.5:54321 ↔ 203.0.113.7:1025` сохраняется в **таблице трансляции**.
4. Ответ приходит на `203.0.113.7:1025`.
5. Роутер по таблице понимает, кому отдать, и **подменяет адрес назначения обратно**.

Это **NAPT** (Network Address Port Translation) — вариант NAT с портами. Именно он позволяет сотням устройств в доме сидеть за одним публичным IP.

### Маршрутизация

Дальше пакет идёт по цепочке **маршрутизаторов** (роутер → провайдер → магистральные сети → ДЦ Google). На каждом узле решение по **таблице маршрутизации** и протоколам (BGP между автономными системами). Обычно 10–20 хопов.

**Проблемы NAT**: ломает end-to-end связность, усложняет P2P, VoIP, игры (нужны STUN/TURN/UPnP).

## 2) TCP Handshake

Классическое **трёхстороннее рукопожатие**:
2.1) **SYN** — клиент: «Хочу соединиться, вот мой начальный seq-номер».
2.2) **SYN + ACK** — сервер: «Согласен, вот мой seq-номер, подтверждаю твой».
2.3) **ACK** — клиент: «Подтверждаю твой».
Соединение установлено.

> Для HTTP/3 вместо TCP используется **QUIC поверх UDP** — handshake выглядит иначе.

## 3) TLS Handshake

### 3.1) Client Hello + SNI

Браузер отправляет:
- **Версию TLS** (1.2, 1.3)
- **Список поддерживаемых шифров** (Cipher Suites) — комбинации алгоритмов обмена ключами, шифрования, хеширования
- **Client Random** — случайное число
- **SNI (Server Name Indication)** — домен `google.com`. Критично: на одном IP живёт много сайтов, сервер по SNI понимает, какой сертификат отдавать

### 3.2) Server Hello

Сервер отвечает:
- Выбранная версия TLS и **шифр**
- **Server Random**
- **Сертификат** — подтверждает, что это `google.com`. Подписан доверенным **CA (Certificate Authority)**
- Возможно, **Server Key Exchange** — доп. данные для обмена ключами

### 3.3) Проверка сертификата (на стороне клиента)

Браузер отвечает на три вопроса: «Кто выдал?», «Кому выдан?», «Ещё действителен?».

**1. Доверие к издателю (цепочка сертификатов)**  
Браузер не доверяет сертификату `google.com` просто так. Он смотрит на **Issuer**. Проверка идёт **по цепочке**:  
`сертификат сервера → промежуточный сертификат → корневой сертификат`

Цепочка валидна, только если «дотягивается» до корневого сертификата, который уже есть в **Trust Store** браузера или ОС.

**2. Соответствие домену**  
Домен из адресной строки сверяется с полем **Subject** или **Subject Alternative Name (SAN)**. Если зашли на `google.com`, а сертификат выдан для `mail.google.com` — ошибка.

**3. Срок действия**  
Текущее время должно быть внутри интервала **Not Before / Not After**.

**4. Статус отзыва (Revocation)** — самый сложный пункт. Сертификат выдан правильно, но приватный ключ украли или сменили владельца → CA отзывает сертификат. Способы проверки:

- **CRL (Certificate Revocation List)** — скачиваем список всех отозванных сертификатов от CA. Минус: списки огромные, качать долго.
- **OCSP (Online Certificate Status Protocol)** — точечный запрос на OCSP Responder про конкретный сертификат. Ответ: `good` / `revoked` / `unknown`.
- **OCSP Stapling** — современный способ. Сервер сам периодически спрашивает у CA статус своего сертификата и «прикрепляет» (stapling) подписанный ответ к сертификату. Браузеру не нужно никуда идти — быстрее и не раскрывает CA, какие сайты вы посещаете.

> **Soft-fail**: если браузер не смог получить информацию об отзыве (OCSP недоступен, сеть лагает), он **может разрешить** соединение. Компромисс между безопасностью и доступностью.

**Где посмотреть в браузере**: замочек в адресной строке → «Сертификат» / «Подключение защищено». Там видны Subject, Issuer, срок действия и путь сертификации.

### 3.4) Обмен ключами и Finished

- Клиент генерирует **Pre-Master Secret**, шифрует его **публичным ключом сервера** (из сертификата) и отправляет.
- Только сервер может расшифровать его **приватным ключом**.
- Теперь у обоих есть: Client Random + Server Random + Pre-Master Secret → выводится **общий сессионный ключ** (симметричный).
- Обе стороны шлют **Finished**, зашифрованный этим ключом — проверка, что обмен не подменили.

Дальше весь трафик идёт **симметричным шифрованием** (быстрее асимметричного).

> **TLS 1.3** — handshake короче: 1-RTT (или 0-RTT при повторном подключении).

## 4) HTTP Request

По зашифрованному каналу уходит:
```
GET / HTTP/2
Host: google.com
User-Agent: ...
Accept: text/html,...
Cookie: ...
```
Метод, путь, заголовки, возможно тело (для POST).

## 5) Обработка на сервере

### 5.1) Балансировщик (Load Balancer)

Первая точка входа. Распределяет запросы между серверами.
- **L4 (TCP)** — балансирует по IP/порту
- **L7 (HTTP)** — смотрит на URL, заголовки, cookie

Примеры: Google Maglev, AWS ELB, HAProxy, Nginx.

### 5.2) Nginx (edge-сервер)

Принимает HTTP-запрос.
- Статика (CSS, JS, картинки) — отдаёт сразу
- Динамика — проксирует дальше
- Здесь обычно **SSL termination**: TLS расшифровывается на edge, внутри ДЦ трафик идёт по HTTP

### 5.3) Reverse Proxy на бэкенд

Nginx выступает как **reverse proxy**:
- скрывает бэкенд от внешнего мира
- кэширует
- балансирует
- применяет rate limiting

Запрос уходит на **бэкенд-приложение** (Python / Go / Java-сервис).

### 5.4) Доступ к БД

Приложение обращается к **базе данных** (PostgreSQL, MySQL, Bigtable и т.п.). Перед БД часто стоит кэш (Redis / Memcached).

Приложение формирует HTML/JSON.

---

## 6) HTTP Response

Ответ идёт обратно по той же цепочке:
```
HTTP/2 200 OK
Content-Type: text/html
Content-Encoding: gzip
...
<html>...</html>
```

Бэкенд → Nginx → балансировщик → интернет → NAT роутера → твой браузер.
---
## 7) Rendering

1. **Парсинг HTML** → **DOM**
2. **Парсинг CSS** → **CSSOM**
3. **DOM + CSSOM → Render Tree**
4. **Layout (Reflow)** — расчёт позиций и размеров
5. **Paint** — отрисовка пикселей
6. **Composite** — сборка слоёв (часто на GPU)

Параллельно:
- Загружаются **подресурсы** (картинки, шрифты, JS) — для каждого нового домена снова DNS → TCP → TLS → HTTP
- Выполняется **JavaScript**, который может менять DOM → повторный Layout/Paint

## 🗺️ Сводная карта пути

|№|Этап|Что происходит|Ключевые сущности|
|---|---|---|---|
|0|Ввод URL|Браузер решает, что делать|—|
|1|DNS|Имя → IP|Кэши, резолвер, корневой сервер, TLD `.com`, авторитативный NS, TTL|
|1.5|NAT + маршрутизация|Пакет уходит в интернет|Приватный/публичный IP, NAPT, таблица трансляции, BGP, хопы|
|2|TCP|Установка соединения|SYN, SYN-ACK, ACK|
|3|TLS|Шифрование|Client Hello, SNI, Server Hello, сертификат, CA, Trust Store, OCSP, сессионный ключ|
|4|HTTP Request|Отправка запроса|Метод, заголовки, Host, Cookie|
|5|Сервер|Обработка|Балансировщик, Nginx, Reverse Proxy, бэкенд, БД|
|6|HTTP Response|Ответ клиенту|Статус, заголовки, тело|
|7|Rendering|Отрисовка|DOM, CSSOM, Layout, Paint, Composite, JS|
