Kubernetes, разработанный компанией Google, опирается на более чем десятилетний опыт выполнения сложных рабочих задач. В результате он стал важнейшим инструментом в сфере DevOps для оркестрации микросервисов. С момента создания Kubernetes был передан в дар [Cloud Native Computing Foundation](https://www.cncf.io/), где стал золотым стандартом отрасли. Крайне важно понимать аспекты безопасности контейнеров K8. Вероятно, во время нашего теста на проникновение мы сможем получить доступ к одному из множества контейнеров.

Одной из ключевых особенностей Kubernetes является его адаптивность и совместимость с различными средами. Эта платформа предлагает широкий спектр функций, которые позволяют разработчикам и системным администраторам легко настраивать, автоматизировать и масштабировать свои развертывания и приложения. Благодаря этому Kubernetes стал популярным решением для организаций, стремящихся оптимизировать процессы разработки и повысить эффективность.

Kubernetes — это система оркестрации контейнеров, которая позволяет запускать все приложения в контейнерах, изолированных от хост-системы с помощью `multiple layers of protection`. Такой подход гарантирует, что на работу приложений не повлияют изменения в хост-системе, например обновления или исправления безопасности. Архитектура K8s состоит из `master node` и `worker nodes`, каждый из которых выполняет определенные функции.

## Концепция K8s

В основе Kubernetes лежит концепция подов, которые могут содержать один или несколько тесно связанных контейнеров. Каждый под функционирует как отдельная виртуальная машина на узле, имеющая собственный IP-адрес, имя хоста и другие характеристики. Kubernetes упрощает управление несколькими контейнерами, предлагая инструменты для балансировки нагрузки, обнаружения сервисов, оркестрации хранилищ, самовосстановления и многого другого. Несмотря на проблемы с безопасностью и управлением, K8s продолжает развиваться и совершенствоваться, предлагая такие функции, как `Role-Based Access Control` (`RBAC`), `Network Policies`, и `Security Contexts`, обеспечивая более безопасную среду для приложений.

Различия между K8 и Docker

|**Функция**|**Докер**|**Kubernetes**|
|---|---|---|
|`Primary`|Платформа для контейнеризации приложений|Инструмент оркестрации для управления контейнерами|
|`Scaling`|Ручное масштабирование с помощью Docker swarm|Автоматическое масштабирование|
|`Networking`|Единая сеть|Сложная сеть с политиками|
|`Storage`|Объемы|Широкий выбор вариантов хранения|

Архитектура Kubernetes в основном делится на два типа компонентов:

- `The Control Plane` (главный узел), который отвечает за управление кластером Kubernetes
- `The Worker Nodes` (миньоны), где запускаются контейнерные приложения

#### Узлы

На главном узле размещается Kubernetes `Control Plane`, который управляет и координирует все действия в кластере, а также обеспечивает поддержание желаемого состояния кластера. С другой стороны, `Minions` выполняют фактические приложения, получают инструкции от Control Plane и обеспечивают достижение желаемого состояния.

Он универсален и может удовлетворить различные потребности, например в поддержке баз данных, рабочих нагрузок искусственного интеллекта и машинного обучения, а также облачных микросервисов. Кроме того, он способен управлять ресурсоемкими приложениями на периферии и совместим с различными платформами. Таким образом, его можно использовать в общедоступных облачных сервисах, таких как Google Cloud, Azure и AWS, или в частных локальных центрах обработки данных.

#### Уровень управления

Уровень управления служит для организации работы. Он состоит из нескольких важнейших компонентов, в том числе:

|**Обслуживание**|**Порты TCP**|
|---|---|
|`etcd`|`2379`, `2380`|
|`API server`|`6443`|
|`Scheduler`|`10251`|
|`Controller Manager`|`10252`|
|`Kubelet API`|`10250`|
|`Read-Only Kubelet API`|`10255`|

Эти элементы позволяют `Control Plane` принимать решения и дают полное представление обо всем кластере.

#### Миньоны

В контейнерной среде `Minions` (рабочие узлы) служат местом для запуска приложений. Важно отметить, что каждый узел управляется и контролируется уровнем управления, что обеспечивает бесперебойную и эффективную работу всех процессов в контейнерах.

`Scheduler` на основе `API server` определяет состояние кластера и соответствующим образом распределяет новые поды по узлам. Определив, на каком узле должен работать под, сервер API обновляет `etcd`.

Чтобы понять, как работают Kubernetes, необходимо разобраться во взаимодействии этих компонентов. Сервер API является точкой входа для всех административных команд, отправляемых пользователями через kubectl или контроллерами. Этот сервер взаимодействует с etcd для получения или обновления состояния кластера.

#### Меры безопасности K8

Безопасность Kubernetes можно разделить на несколько направлений:

- Безопасность кластерной инфраструктуры
- Безопасность конфигурации кластера
- Безопасность приложений
- Безопасность данных

Каждый домен включает в себя множество уровней и элементов, которые должны быть должным образом защищены и управляемы разработчиками и администраторами.

## Kubernetes API

Основой архитектуры Kubernetes является его API, которое служит основным каналом взаимодействия для всех внутренних и внешних процессов. Kubernetes API разработан для поддержки декларативного управления, что позволяет пользователям определять желаемое состояние системы. Это дает Kubernetes возможность предпринимать необходимые шаги для достижения желаемого состояния. Kube-apiserver отвечает за размещение API, которое обрабатывает и проверяет RESTful-запросы на изменение состояния системы. Эти запросы могут включать в себя создание, изменение, удаление и получение информации, связанной с различными ресурсами системы. В целом Kubernetes API играет важнейшую роль в обеспечении бесперебойной связи и контроля внутри кластера Kubernetes.

В рамках Kubernetes ресурс API служит конечной точкой, в которой хранится определенная коллекция объектов API. Эти объекты относятся к определенной категории и включают в себя такие важные элементы, как поды, сервисы, развертывания и т. д. Каждый уникальный ресурс имеет свой набор доступных операций, в том числе:

|**Запрос**|**Описание**|
|---|---|
|`GET`|Получает информацию о ресурсе или списке ресурсов.|
|`POST`|Создает новый ресурс.|
|`PUT`|Обновляет существующий ресурс.|
|`PATCH`|Применяет частичные обновления к ресурсу.|
|`DELETE`|Удаляет ресурс.|

#### Аутентификация

Что касается аутентификации, Kubernetes поддерживает различные методы, такие как клиентские сертификаты, токены-носители, прокси-сервер аутентификации или базовая HTTP-аутентификация, которые служат для подтверждения личности пользователя. После аутентификации пользователя Kubernetes принимает решения об авторизации с помощью управления доступом на основе ролей (`RBAC`). Этот метод предполагает назначение пользователям или процессам определенных ролей с соответствующими разрешениями на доступ к ресурсам и работу с ними. Таким образом, процесс аутентификации и авторизации в Kubernetes представляет собой комплексную меру безопасности, которая гарантирует, что только авторизованные пользователи смогут получать доступ к ресурсам и выполнять операции.

В Kubernetes `Kubelet` можно настроить так, чтобы он разрешал `anonymous access`. По умолчанию Kubelet разрешает анонимный доступ. Анонимные запросы считаются не прошедшими аутентификацию, то есть любой запрос, отправленный в Kubelet без действительного клиентского сертификата, будет считаться анонимным. Это может быть проблемой, поскольку любой процесс или пользователь, имеющий доступ к API Kubelet, может отправлять запросы и получать ответы, что может привести к раскрытию конфиденциальной информации или несанкционированным действиям.

#### Взаимодействие с API-сервером K8

        шеллсессия
`cry0l1t3@k8:~$ curl https://10.129.10.11:6443 -k  {     "kind": "Status",     "apiVersion": "v1",     "metadata": {},     "status": "Failure",     "message": "forbidden: User \"system:anonymous\" cannot get path \"/\"",     "reason": "Forbidden",     "details": {},     "code": 403 }`

`System:anonymous` Обычно это означает, что пользователь не прошел аутентификацию, то есть мы не предоставили действительные учетные данные или пытаемся получить доступ к серверу API анонимно. В данном случае мы пытаемся получить доступ к корневому пути, что в случае успеха даст нам значительный контроль над кластером Kubernetes. По умолчанию доступ к корневому пути обычно предоставляется только аутентифицированным и авторизованным пользователям с административными правами, и сервер API отклоняет запрос, возвращая соответствующий код состояния `403 Forbidden` .

## Повышение привилегий
