#protocol #windows #AD #auth 

**Kerberos** — сетевой протокол аутентификации, который предлагает механизм взаимной аутентификации клиента и сервера перед установлением связи между ними через незащищённые сети

> Используется, когда клиент хочет подключиться к какому-то сервису, например  SMB, на каком-то узле example.domain.local

### Терминология _Kerberos_:

- **Билет** (_ticket_) – временные шифрованные данные, выдаваемые клиенту для аутентификации на сервере, на котором располагается необходимая служба.
- **Клиент** (_client_) – некая сущность в сети (пользователь, хост или сервис), которая может получить билет от _Kerberos_.
- **Центр выдачи ключей** (_key distribution center, KDC_) (domain controller (DC)) – сервис, выдающий билеты _Kerberos_.
- **Область** (_realm_) – сеть, используемая _Kerberos_, состоящая из серверов KDC и множества клиентов. Имя _realm_ регистрозависимо, обычно пишется в верхнем регистре и совпадает с именем домена.
- **Принципал** (_principal_) – уникальное имя для клиента, для которого разрешается аутентификация в _Kerberos_. Записывается в виде `root[/instance]@REALM`.

	- Обычно говорят ТИКЕТ, но подразумевают ТИКЕТ + session key, так как без него мы не сможем подписать аутентификатор => воспользоваться ТИКЕТОМ

	- Сервис = SPN + работающий из определенной учетной записи

## Kerberos аутентификация 

1) Аутентификация пользователя
	- AS REQ - запрос TGT
	- AS REP - получение TGT
2) Запрос тикета для получения доступа к сервису
	- TGS REQ - запрос на получение TGS (отправляется TGT + аутентификатор)
	- TGS REP - получение TGS
3) Установление соединения с сервисом, передача TGS по прикладному протоколу
	- AP REQ - аутентификация (отправляется TGS + аутентификатор)
	- AP REP - ответ OK

### Процесс первичной аутентификации

Когда пользователь выполняет первичную аутентификацию, после успешного подтверждения его подлинности, _KDC_ выдаёт первичное **удостоверение пользователя для доступа к сетевым ресурсам** — _Ticket Granting Ticket_ (_TGT_).

![[init auth.png]]

![[KRB_AS_REQ.png]]

KDC в ответ на запрос пользователя отправляет отправляет TGT, который зашифрован секретом самого KDC (krbtgt), а также зашифрованный blob, в котором хранится сессионный ключ, который необходим для использования TGT

### TGS аутентификация

![[KRB_TGS_REQ.png]]
Отправляется TGS запрос (TGS REQ), в котором отправляется TGT и аутентификатор (структура зашифрованная сессионным ключом, взятым на предыдущем шаге), это доказывает, что данный клиент владеет данным TGT, проверяет SPN, который указал клиент

Далее клиент получает от _KDC_ **удостоверение для доступа к конкретному сетевому ресурсу** — _Service Ticket_ (_ticket-granting service, TGS_) **с сессионным ключом**.

### Установление соединения с сервисом
![[NTLM very micro.png]]

Клиент инициирует соединение по прикладному протоколу, делает AP REQ, передает TGS с аутентификатором (зашифрованным сессионным ключом) и если все ок, устанавливает соединение
## Kerberos тикеты - токены аутентификации

> TGT/TGS - токены аутентификации с подписью

1) Тикеты нельзя отозвать, только ротировать общие секреты (причем krbtgt - дважды, необходимо ротировать спустя 10 часов второй раз)
2) TGS - работают даже после блокировки УЗ
3) TGT/TGS содержат старые членства в группах (то есть чтобы применилась новая политика членства в группах, пользователю нужно перелогиниться, чтобы сбросить старый тикет или же отчистить кэш)
4) TGT работают даже после смены пароля пользователя и разблокировки

# Hardening Kerberos

gMSA - это специальный тип доменных учетных записей в среде Active Directory, предназначенный для автоматизации управления паролями сервисов, служб и пулов приложений

1) Патчинг
2) Ограничение машин квоты
3) Уменьшение жизни TGT/TGS билетов
4) Отказ от rc4 в пользу aes256/aes512
5) Регулярная ротация пароля krbtgt
6) Использование gMSA
7) Включение Armoring (FAST)
8) Полное отключение `Do not required kerberos preauth`
9) Отключение `unconstrained delegations` везде, кроме DC
10) Мониторинг аномалий
