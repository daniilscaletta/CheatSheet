## Domain Cached Credentials (MSCache2)

В среде Active Directory методы аутентификации, упомянутые в этом и предыдущем разделах, требуют, чтобы хост, к которому мы пытаемся получить доступ, взаимодействовал с «мозгом» сети — контроллером домена. Компания Microsoft разработала [алгоритм MS Cache v1 и v2](https://web.archive.org/web/20240121113925/https://webstersprodigy.net/2014/02/03/mscash-hash-primer-for-pentesters/) (также известный как `Domain Cached Credentials`(DCC) для решения потенциальной проблемы, когда хост, подключенный к домену, не может взаимодействовать с контроллером домена (например, из-за сбоя сети или другой технической проблемы), и, следовательно, аутентификация NTLM/Kerberos не работает для доступа к данному хосту. Хосты сохраняют последний `ten`хеши для всех пользователей домена, успешно вошедших в систему на этом компьютере. `HKEY_LOCAL_MACHINE\SECURITY\Cache`Ключ реестра. Эти хеши нельзя использовать в атаках типа «передача хеша». Кроме того, взлом хеша с помощью такого инструмента, как Hashcat, происходит очень медленно, даже при использовании чрезвычайно мощной системы взлома на базе графического процессора, поэтому попытки взлома этих хешей обычно должны быть крайне целенаправленными или основываться на использовании очень слабого пароля. Эти хеши могут быть получены злоумышленником или специалистом по тестированию на проникновение после получения локального административного доступа к хосту и имеют следующий формат: `$DCC2$10240#bjones#e4e938d12fe5974dc42a90120bd9c90f`

## LDAP

_LDAP_ (_Lightweight Directory Access Protocol_), или облегчённый протокол доступа к каталогам, является открытым коммуникационным протоколом, используемым для хранения и получения данных из каталога с иерархической структурой. Он определяет методы, в которых служба каталога может быть доступна. Обычно используется для хранения информации об организации, её активах и пользователях. _LDAP_ является гибким решением для определения любого типа сущностей и их свойств.

Говоря более широко, _LDAP_ формирует способ, которым данные внутри службы директории должны быть представлены пользователям, определяет требования к компонентам, используемым для создания записей данных внутри службы директории, и описывает способ, которым различные примитивные элементы используются для составления записей.

Поскольку _LDAP_ является открытым протоколом, существует множество различных реализаций. Проект **OpenLDAP** является одним из наиболее хорошо поддерживаемых вариантов с открытым исходным кодом. Клиентские библиотеки _LDAP_ доступны практически для любого фреймворка, а реализовать интеграцию относительно легко.

Сегодня мы чаще слышим об этом протоколе как механизме аутентификации в сторонних приложениях. Но несмотря на то, что применение _LDAP_ может помочь решить задачу внедрения аутентификации пользователей в различных приложениях компании, оно создаёт множество проблем. В отличие от специально предназначенных протоколов аутентификации, при использовании _LDAP_ возникают различные уязвимости информационной безопасности.

> Пароль пользователя или секрет аутентификации должен оставаться секретом. Он должен быть известен только самому пользователю и системе аутентификации. При использовании _LDAP_-аутентификации пользователь вынужден поделиться своим секретом с третьей стороной, чтобы она затем смогла использовать данный секрет для взаимодействия с _LDAP_-каталогом от имени пользователя.

При использовании специально предназначенных протоколов аутентификации, таких как _Kerberos_ и даже раннего _NTLM_, секрет пользователя не передаётся по сети. Клиентское устройство и сервер используют криптографические операции, чтобы доказать друг другу, что у них один и тот же секрет и не обмениваются самим секретом.

Проблема заключается в том, что если один сервер приложений скомпрометирован, то все учётные данные, которыми пользовались их владельцы во время атаки, также скомпрометированы. Под угрозой находится и любая другая система, которая использует тот же каталог _LDAP_ для аутентификации.

Кроме того _LDAP_-сервер не может гарантировать безопасность транзакции. Несмотря на то, что _LDAP_-сервер, например, может обеспечить принудительное выполнение операции _bind_ по _TLS_, чтобы гарантировать, что учётные данные не передаются в открытом виде, сам сервер никогда не принимал никакой роли в получении учётных данных от пользователя. Существует риск, что приложение будет получать пароль по **небезопасному** каналу.

При этом доверие операции _bind_ также не может быть полным, так как существует возможность выполнения операции _bind_ без проверки подлинности — одна из тонкостей протокола, о которой не знают многие опытные специалисты по _LDAP_.

Многофакторная аутентификация и единый вход крайне трудно реализуемы в схеме с _LDAP_. Поэтому для аутентификации в приложениях лучше выбрать современный способ, предназначенный для этого.


## SSO

_Single sign-on_ (_SSO_), она же прозрачная авторизация, это идея, по которой пользователь раз вводит логин/пароль своей учётной записи в _Active Directory_ при входе на компьютер, и дальше, открывая, например, веб-приложение уже автоматически авторизуется с данными своей учётки.

В браузерах для этого заложен принцип — получая в ответ на свой _Get_-запрос _HTTP_-код 401 «_Not Authorized_», и в HTTP-заголовках _<WWW-Authenticate: Negotiate>_, он, браузер, делает запрос в _KDC_ (_Key Distribution Center_ — одна из служб _AD_) на получение специального _SPNEGO_-токена для данного веб-сервиса. Если учётки для такого веб-сервиса нет в _AD_, то браузер берёт стандартный ответ для авторизации по _NTLM_. Но в данном случае мы считаем, что что-то пошло не так.

В случае корректных настроек данного веб-сервиса в _AD_, браузер на ответ 401 вновь отправляет _Get_-запрос, но уже с заголовком вида _<Authorization: YIIJvwYGKw… >_. Если токен начинается так, с «_YII_», значит это _Kerberos_-закодированный тикет, содержащий данные для авторизации.

Далее веб-сервис, получив токен, с помощью _Kerberos_-клиента отправляет его в _KDC_ на проверку. И, в случае успеха, получает имя пользователя в AD. Которое дальше уже можно использовать для поиска данных о пользователе (например, групп, в которых он состоит) уже через другой сервис доступа к AD — _LDAP_.

Для включения _SSO_ необходимо задать в _AD SPN_-имя для веб-сервиса (вида _HTTP/webservice.example.com@EXAMPLE.COM_). Это позволит клиентским браузерам запрашивать токен для данного сервиса и передавать его в _HTTP_-заголовке веб-сервису, а _Kerberos_-клиенту через данный сервис на основе ключа проверять подлинность пользователей. После этого сформировать для этого сервиса ключ _krb5.keytab_, который будет использоваться в _Kerberos_-клиенте для проверки подлинности пользователей.
