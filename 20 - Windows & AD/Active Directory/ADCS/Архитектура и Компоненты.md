# Иерархия ЦС (CA Hierarchy)
В реальных сетях почти никогда не бывает одного единственного сервера AD CS. Используется многоуровневая структура.

1. **Root CA (Корневой ЦС):** Самый главный. Он подписывает сертификаты для подчиненных ЦС. В безопасных средах он **Offline** (выключен и физически отключен от сети), чтобы его закрытый ключ нельзя было украсть по сети.

2. **Subordinate / Issuing CA (Подчиненный / Издающий ЦС):** Именно он «живет» в домене, общается с пользователями и выдает им сертификаты.


- **Trust Anchor (Якорь доверия):** Публичный сертификат Root CA, который копируется на все машины через AD.
- **CDP (CRL Distribution Point):** Путь (HTTP или LDAP), по которому клиенты забирают списки отзыва. Root CA может быть выключен, но CDP должен быть доступен всегда.

## Компоненты системы
Чтобы это работало, <span style="background:#b1ffff">внутри Windows Server крутятся следующие части:</span>

- **Certification Authority (CA):** Сама служба, которая хранит закрытый ключ и подписывает запросы
- **Certificate Database:** База данных всех выданных, просроченных и отозванных сертификатов
- **Certificate Templates:** «Чертежи», по которым создаются сертификаты 
- **CRL (Certificate Revocation List):** «Черный список» сертификатов, которым больше нельзя доверять.

> Offline ROOT CA - это **"ядерная кнопка"** Blue Team

<span style="background:#ff4d4f">Если хакеры захватили Issuing CA,</span> они могут выпускать любые сертификаты от его имени. Это катастрофа. Но если у нас есть **<font color="#76923c">Offline Root CA</font>**:

1. **Отзыв доверия:** Мы включаем Root CA (физически), выпускаем новый список отзыва (**CRL**), в который вносим сертификат скомпрометированного Issuing CA.

2. **Восстановление:** Все компьютеры в домене видят, что их "издатель" теперь в черном списке, и перестают принимать его сертификаты. Мы выпускаем новый Issuing CA, подписанный тем же Root CA, и жизнь продолжается.

3. **Безопасность ключа:** Пока Root CA выключен, его закрытый ключ невозможно достать удаленно. Это "корень доверия", который остается чистым.

### Доверие в Active Directory (NTAuthCertificates)

**NTAuthCertificates** — это объект в контейнере `Configuration` (AD), который служит «белым списком» Центров Сертификации (CA).

- **Функция:** Контроллер домена (KDC) разрешает вход по сертификату (PKINIT) **ТОЛЬКО** если выпустивший его ЦС прописан в этом списке.

- **Различие с CRL:** **CRL** — список «плохих» сертификатов (отозванных).
- **NTAuthCertificates** — список «доверенных» заводов (ЦС), которым разрешено выдавать пропуска в домен.

- **Путь в AD:** `CN=NTAuthCertificates,CN=Public Key Services,CN=Services,CN=Configuration,DC=...`


# Интеграция с AD

Enterprise CA неразрывно связан с AD. Все данные о том, какие у нас есть центры сертификации и какие шаблоны они поддерживают, хранятся в специальном разделе базы данных AD — **Configuration Partition**.

Это критически важный момент для исследователя. Если обычный раздел (Domain Partition) содержит пользователей и группы, то Configuration Partition **реплицируется на все контроллеры домена в лесу**.

Рядовой компьютер в любом филиале узнает об этом благодаря тому, что он постоянно взаимодействует со «своим» контроллером домена. Windows-клиенты используют протокол **LDAP**, чтобы опрашивать определенные объекты в контейнере `Public Key Services`

> <font color="#ffff00">Сервер AD CS (Enterprise CA) целиком и полностью доверяет AD, поэтому если у нас есть права на изменение объектов `CN=`, то сможем подменить сертификат</font>

# Механизмы доступа
Клиент находит путь к данным о сертификатах:

1. **Поиск точки входа:** Клиент ищет в AD объект класса `pKIEnrollmentService`. Это «визитная карточка» сервера AD CS.

2. **Чтение параметров:** Через LDAP клиент выкачивает атрибуты этого объекта (например, `dNSHostName`, чтобы знать, куда отправлять запрос на сертификат, и `certificateTemplates`, чтобы знать, какие типы сертификатов этот сервер умеет выдавать).
