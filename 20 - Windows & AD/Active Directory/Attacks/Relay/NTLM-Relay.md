> NTLM-Relay - разновидность MITM атаки, при которой атакующий аутентифицируется от имени пользователя на сервере

![[Pasted image 20260919054217.png]]

Можно использовать различные протоколы:
- SMB
- LDAP
- DCOM
- HTTP
- WinRM
- MSSQL и тд

# Этапы проведения атаки NTLM-Relay

1) Pre-Relay - Вызов аутентификации на пользователя (Poisoning/Spoofing  Coersion)
2) Relay 
3) Post-Relay


## 1) Pre-Relay Фаза

#### 1) SSRF-like примитив (coerce)

Когда возможно указать серверу адрес подключения, для того чтобы он сам инициировал его, а в качестве адреса указать себе (работает в printer bug)

#### 2) Активная MITM атака

![[Pasted image 20260919054544.png]]

Используется любая спуфинг атака, с целью встать посередине между сервером и клиентом, для дальнейшего перехвата NTLM сессии

Анализ трафика в сети при помощи Responder/Pretender 
```bash
sudo python3 Responder.py -I ens192 -A # НЕ отравлять трафик
```


Чтобы отравить широковещательный трафик, а не анализировать его, мы можем отключить опцию `-A`; `Responder` будет отвечать на широковещательный трафик и отправлять отравленные ответы, заставляя пользователей пытаться пройти аутентификацию на нашей атакующей машине и соответсnвенно получить данные аутентификации NTLM
```bash
sudo python3 Responder.py -I ens192 # Отравлять трафик
```

# Защита от NTLM-Relay

### 1) Signing 

При включенной в **принудительном** режиме функции у нас каждый пакет (SMB-signing, LDAP-signing,...) будет подписываться, что не дает сделать relay

Без signing мы можем перехватить NTLM аутентификацию, но дальше мы не сможем подписывать пакеты => соединение разорвется

### 2) Channel binding

Добавляется Channel Binding Token (CBT) в протокол аутентификации

При формировании response, клиент также опирается на CBT, так как он формируется криптографически, то предполагается, что его нельзя скомрометировать

### 3) Service validation

Менее распространена
Проверяет SPN из аутентификации
